# 外部对接与 SQL API 双凭证体系设计

## 目标

将现有职责交叉的第三方密钥与 API Builder 密钥重构为两套独立凭证体系：

- 第三方签名凭证服务于后台系统整合、数据同步和业务开放接口。
- SQL API 调用凭证只服务于 API Builder 生成的动态接口。
- 两套凭证不共用数据表、认证中间件或授权关系，也不能换取后台用户身份。

当前尚无真实厂商接入，因此旧凭证不做兼容迁移，全部废弃并重新签发。

## 非目标

- 不改造后台管理员的账号密码、短信或 JWT 登录流程。
- 不让第三方凭证直接调用 API Builder 动态接口。
- 不让 SQL API 凭证访问普通后台管理接口。
- 不在本次改造中建设 OAuth2、开放平台门户或开发者自助注册流程。

## 设计原则

1. 每套凭证只表达一种身份和一种认证方式。
2. 外部调用方不继承密钥创建者的后台角色或权限。
3. 默认拒绝未明确授权的接口。
4. 完整 Secret 或 API Key 仅在创建、轮换时展示一次。
5. 日志中不得记录完整凭证、签名或敏感请求正文。
6. 状态、有效期、授权范围和限流在请求进入业务逻辑前完成校验。

## 系统一：第三方签名凭证

### 定位

第三方签名凭证代表一个外部后台系统或合作方，用于调用平台显式开放的集成接口，例如用户同步、订单同步、数据查询和状态回传。

### 请求协议

调用方必须通过请求头提交：

```text
X-API-Key: <public_key>
X-Timestamp: <unix_timestamp_ms>
X-Nonce: <random_nonce>
X-Signature: <hmac_sha256_hex>
```

签名原文采用固定格式：

```text
HTTP_METHOD\n
CANONICAL_PATH_AND_QUERY\n
TIMESTAMP\n
NONCE\n
SHA256_BODY
```

- `HTTP_METHOD` 使用大写。
- `CANONICAL_PATH_AND_QUERY` 使用不含域名的标准化路径，并附加按键名和值排序、统一编码后的查询字符串。
- `TIMESTAMP` 使用毫秒级 Unix 时间戳。
- `NONCE` 每次请求必须唯一。
- `SHA256_BODY` 是原始请求体字节的 SHA-256；无请求体时计算空字节摘要。
- 最终签名为 `HMAC-SHA256(api_secret, canonical_request)` 的十六进制字符串。
- 服务端必须在 JSON 解析前保留原始请求体字节，避免序列化差异导致合法签名失败。

### 验证流程

1. 校验四个签名请求头是否齐全。
2. 根据公开 Key 查询启用的第三方凭证。
3. 校验有效期和调用方状态。
4. 校验时间戳与服务器时间差不超过 5 分钟。
5. 使用 Redis 原子写入 Nonce，缓存时间 10 分钟；已存在则拒绝。
6. 解密 API Secret，计算签名并使用恒定时间比较。
7. 校验该凭证是否包含当前路由要求的权限标识。
8. 将调用方身份写入请求上下文，进入业务处理。
9. 异步更新最后使用时间并记录调用审计。

### 路由授权

开放接口显式声明权限标识，例如：

```js
verifyThirdPartySignature('user:sync')
verifyThirdPartySignature('order:read')
```

凭证保存一组权限标识。未声明签名中间件的普通后台接口不能被第三方凭证访问。

### 数据模型

保留 `owl_third_party_api_keys` 作为第三方凭证主表，调整为：

| 字段 | 说明 |
|---|---|
| `id` | 内部 UUID |
| `client_name` | 外部系统或厂商名称 |
| `api_key` | 可公开的唯一标识 |
| `secret_ciphertext` | AES-256-GCM 加密后的 Secret |
| `secret_iv` | 加密随机向量 |
| `secret_auth_tag` | GCM 校验标签 |
| `scopes` | JSON 权限标识数组 |
| `status` | `active` / `inactive` |
| `expires_at` | 可选过期时间 |
| `last_used_at` | 最后成功调用时间 |
| `description` / `remark` | 管理信息 |
| 审计字段 | 创建、更新、删除人员及时间 |

Secret 加密密钥必须来自独立环境变量，不复用 JWT Secret。列表接口不返回可恢复的 Secret，也不返回伪造的脱敏 Secret，只显示“已配置”。

## 系统二：SQL API 调用凭证

### 定位

SQL API 调用凭证代表一个使用 API Builder 接口的厂商或业务应用。一个凭证可以被授权访问多个指定的 SQL 接口。

### 请求协议

调用方只通过请求头提交：

```text
X-API-Key: <api_key>
```

不支持 Query 参数传递密钥，不支持用该密钥调用 `/auth/api-token` 换取后台 JWT，也不接受将其放入后台用户的 `Authorization` 头。

### 验证流程

1. 从 `X-API-Key` 读取凭证。
2. 使用独立服务端 Pepper 对完整 Key 计算 HMAC-SHA256，并通过带索引的摘要查找凭证。
3. 校验状态和有效期。
4. 根据请求路径、版本和 HTTP 方法找到 SQL 接口。
5. 校验“密钥—接口”授权关系。
6. 按接口配置和密钥维度执行每分钟限流。
7. 将调用方身份和密钥 ID 写入请求上下文。
8. 执行参数校验和 SQL 接口逻辑。
9. 更新最后使用时间并写入调用日志。

### 数据模型

`owl_api_keys` 调整为调用方凭证主表：

| 字段 | 说明 |
|---|---|
| `id` | 内部 UUID，不作为外部凭证 |
| `client_name` | 厂商或业务应用名称 |
| `key_prefix` | 用于列表展示和快速定位 |
| `key_hash` | 完整 API Key 的 HMAC-SHA256 摘要，建立唯一索引 |
| `status` | `active` / `inactive` |
| `expires_at` | 必填过期时间，默认创建后 180 天 |
| `last_used_at` | 最后成功调用时间 |
| `description` | 用途说明 |
| 审计字段 | 创建、更新、删除人员及时间 |

新增 `owl_api_key_interfaces` 授权关系表：

| 字段 | 说明 |
|---|---|
| `id` | 内部 UUID |
| `api_key_id` | SQL API 凭证 ID |
| `interface_id` | API Builder 接口 ID |
| `created_by` / `created_at` | 授权审计信息 |

`api_key_id + interface_id` 建立唯一约束。删除密钥或 SQL 接口时级联删除授权关系。

删除旧的 `ApiKey.interface_id` 和 `ApiInterface.api_key_id`，避免双向重复关系。

### Key 生成与存储

- Key 使用足够强度的随机字节生成，并带可识别前缀，例如 `oak_`。
- 数据库只保存前缀和使用独立 `API_KEY_PEPPER` 生成的摘要。
- 完整 Key 只在创建或重新生成时返回一次。
- 重新生成后旧 Key 立即失效，授权接口保持不变。

## 管理端交互

### SQL API 密钥页面

- 页面名称使用“接口密钥”，说明其仅用于 SQL API 调用。
- 列表使用统一 `DataTable`，展示厂商名称、Key 前缀、授权接口数、状态、有效期和最后使用时间。
- 创建和编辑表单包含厂商名称、说明、有效期以及 SQL 接口多选。
- 创建或重新生成后使用一次性凭证弹窗，提供复制操作和明确的保存提示。
- 支持启用、禁用、重新生成、修改授权和删除。
- 接口开发列表中的“管理密钥”入口复用同一授权组件，并按当前接口筛选关联凭证，不再维护第二套密钥逻辑。

### 第三方密钥页面

- 页面名称使用“第三方签名密钥”。
- 列表展示客户端名称、API Key、权限范围、状态、有效期和最后使用时间。
- 创建和编辑表单包含客户端信息、权限范围和有效期。
- 创建或轮换 Secret 后使用一次性凭证弹窗。
- 提供固定的签名规范说明，示例必须与后端规范由同一组常量或测试约束保持一致。
- 使用统一列表、搜索、分页、空状态、加载状态和确认弹窗组件。

## 接口与服务边界

### 第三方签名凭证服务

负责凭证生命周期、Secret 加解密、签名验证、Nonce 防重放和权限标识判断。业务控制器只读取已验证的第三方调用方上下文。

### SQL API 凭证服务

负责 Key 生命周期、哈希验证、接口授权关系和限流。API Builder 执行器只接收已经通过授权的调用方上下文。

### 禁止交叉

- 第三方签名中间件不查询 `owl_api_keys`。
- SQL API 认证中间件不查询 `owl_third_party_api_keys`。
- 后台 JWT 登录服务不查询任一外部凭证表。
- 两套凭证使用不同的请求上下文字段和审计类型。

## 错误响应

| 状态码 | 场景 |
|---|---|
| `400` | 签名请求头、时间戳或请求格式无效 |
| `401` | 缺少凭证、凭证不存在或签名错误 |
| `403` | 凭证禁用、过期或无当前接口权限 |
| `409` | Nonce 已使用，疑似重放请求 |
| `429` | 超过接口或调用方频率限制 |

对外错误信息不区分“Key 不存在”和“Secret 错误”等可用于枚举凭证的细节；详细原因仅写入安全日志。

## 审计与可观测性

两套凭证均记录：

- 凭证 ID 和调用方名称；
- 请求路径、HTTP 方法和来源 IP；
- 响应状态、耗时和发生时间；
- 验证失败分类，但不记录秘密值；
- 创建、禁用、轮换、授权变更和删除操作。

API Builder 继续使用接口调用日志；第三方集成使用独立审计类型，避免与后台用户操作日志混合。

## 废弃与迁移

由于没有真实厂商接入，本次采用一次性清理：

1. 删除现有两类密钥数据及旧关联，不迁移明文凭证。
2. 创建新的字段、索引和 `owl_api_key_interfaces` 授权表。
3. 移除 `/auth/api-token` 的 API Key 登录路由、校验和前端说明。
4. 移除 Query 参数、Bearer API Key 等非标准入口，只保留 `X-API-Key`。
5. 修正 API Builder 自定义路由上的认证中间件挂载顺序。
6. 保留现有 SQL 接口定义，但所有受保护接口在重新授权前拒绝外部访问。
7. 部署后由管理员重新创建两类凭证并分配权限。

数据库变更必须通过项目迁移机制完成，不依赖应用启动时自动修改表结构。

## 验证范围

### 第三方签名

- 正确签名可通过。
- 请求体、路径、方法、时间戳或 Nonce 任一变化都会失败。
- 重复 Nonce、过期时间戳、禁用凭证、过期凭证和缺少权限均被拒绝。
- 多实例通过 Redis 共享 Nonce 状态。

### SQL API 密钥

- 一个凭证可以调用多个已授权接口。
- 同一凭证不能调用未授权接口。
- 禁用、过期、重新生成和删除后旧 Key 立即失效。
- Query 参数、Bearer 和 `/auth/api-token` 不再接受 SQL API Key。
- 限流按照调用方与接口组合生效。

### 管理端

- 列表不泄露完整 Secret 或 API Key。
- 一次性凭证弹窗只在创建、轮换成功后出现。
- 两类页面使用统一列表和表单交互规范。
- 接口列表与接口密钥页面使用同一授权数据源。

## 完成标准

- 第三方签名凭证与 SQL API 调用凭证的数据、路由和认证代码完全分离。
- 外部凭证不能换取或继承后台用户权限。
- SQL API 凭证可以被授权访问多个接口，且不能越权访问其他接口。
- 第三方开放接口具备签名、防篡改、防重放和权限范围校验。
- 旧密钥全部废弃，管理界面和文档不再展示旧调用方式。
- 安全日志、调用日志和错误响应符合本设计约束。
